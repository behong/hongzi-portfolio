01 · 프로젝트 소개

왜 체결 메시지를 자동으로 수집하려 했나

주식 체결이 이뤄지면 증권사(한국투자증권) 카카오톡 채널로 체결 안내 메시지가 도착합니다. 체결가, 수량, 주문번호가 담긴 긴 메시지인데, 이걸 매매일지에 옮겨 적는 일은 번거롭고 빠뜨리기도 쉽습니다. 휴대폰이 스스로 체결 메시지를 읽어 서버로 보내 주면, 기록은 자동으로 쌓이고 사람은 매매에만 집중할 수 있습니다.

문제는 카카오톡 알림만으로는 긴 메시지를 온전히 가져올 수 없다는 점입니다. 이 프로젝트는 그 한계를 확인하고, 알림이 아니라 채팅 화면 자체를 읽는 방식으로 우회해 전문(全文)을 서버까지 전달하는 핵심 기술을 먼저 검증한 기록입니다. 자동 실행의 마지막 단계와 DB 저장은 아직 남아 있으며, 이 페이지에서는 검증된 것과 아닌 것을 엄격히 구분해 표시합니다.

05 · 알림 필터링

카카오톡 알림 필터링으로 불필요한 자동 실행 방지

자동 실행의 조건을 좁히는 단계입니다. 설정은 진행 중이고, 실제 체결 알림에서의 동작은 아직 검증되지 않았습니다.

기존 문제. 알림 트리거를 그대로 연결하면 카카오톡 메시지가 하나만 도착해도 MacroDroid가 실행돼 한국투자증권 채팅방을 열고, 화면을 읽어 서버로 전송합니다. 친구의 일상 메시지에도 휴대폰 화면이 멋대로 전환되고 불필요한 HTTP 요청이 발생하는 구조였습니다.

개선. 알림의 제목에 ‘한국투자증권’이 포함되고 본문에 ‘체결안내’가 포함될 때만 실행되도록 이중 필터를 설정했습니다. 두 조건을 모두 만족해야(AND) 매크로가 동작하므로, 일반 알림과 증권사의 일반 공지는 실행 전에 걸러집니다.

도입 전 문제

카카오톡 알림이 하나만 와도 매크로가 실행됐습니다. 친구가 보낸 메시지에도 채팅방이 열리고 화면 읽기와 서버 전송이 일어나, 불필요한 화면 전환과 HTTP 요청이 발생했습니다.

도입 후 — 기대 동작 설정 중 · 미검증

제목과 본문 조건을 모두 만족하는 체결안내 알림에서만 실행됩니다. 일반 친구의 알림에는 반응하지 않고, 한국투자증권의 일반 공지도 조건에 따라 제외되며, 불필요한 화면 전환과 HTTP 요청이 줄어듭니다. 단, 실제 알림의 제목과 본문에 지정한 문자열이 그대로 들어 있어야 하며, 카카오톡의 알림 표시 방식에 따라 정상 체결 메시지를 놓칠 가능성도 있습니다.

실제 검증 상태. 현재까지 확인된 것은 제목 필터가 설정 화면에 들어가 있는 것까지입니다. 나머지는 아직 확인되지 않았습니다.

보안상 남은 문제. 이 필터는 자동화의 실행 조건일 뿐, 실행된 뒤 화면에서 읽은 다른 메시지가 서버로 함께 전송되는 문제까지 해결하지는 못합니다. 화면 텍스트 전체 읽기는 채팅방에 보이는 여러 메시지를 한꺼번에 수집할 수 있어서, 실제로 테스트 중에는 채팅방 화면에 있던 임시비밀번호 발급 안내가 서버로 전달된 사례가 있었습니다. 그래서 서버에서 체결안내 메시지만 식별하는 판정, 비밀번호·인증정보 같은 민감정보의 저장 방지, 주문번호와 거래일을 이용한 중복 검증이 후속 작업으로 남아 있고, 화면 잠금 상태의 자동 실행 검증과 실제 체결 알림에서의 필터 동작 확인도 함께 필요합니다.

07 · 기술적 한계

알고 넘어가야 할 것들

잠금·화면 꺼짐 상태

화면이 꺼져 있거나 휴대폰이 잠긴 상태에서는 UI 자동조작이 실패할 수 있습니다. 무인 자동 실행의 가장 큰 변수입니다.

화면에 보이는 것만 읽힌다

화면 텍스트 읽기는 현재 화면에 표시된 내용만 가져옵니다. 스크롤 밖에 있거나 화면에 표시되지 않은 메시지는 추출할 수 없습니다.

카카오톡 UI 변경에 취약

카카오톡 화면 구조나 View ID가 업데이트로 달라지면 채팅방 자동 열기와 텍스트 읽기가 깨질 수 있어, 그때마다 설정을 손봐야 합니다.

개인정보 전송 위험

화면 전체를 읽는 방식이라 비밀번호 등 민감정보가 화면에 있으면 함께 전송될 수 있습니다. 전송 전 민감정보 차단은 아직 구현하지 않았습니다. 실제로 테스트 중 채팅방 화면에 있던 임시비밀번호 발급 안내가 서버로 전달된 사례가 있었습니다.

과거 메시지를 현재 거래로 오인할 위험

채팅방에 남은 과거 체결 메시지를 오늘 거래로 저장하면 안 됩니다. 거래일 검증은 아직 구현하지 않았으므로, 지금 단계의 수집 데이터는 기록용으로만 봅니다.

중복 방지 미구현 · 테스트와 실전의 구분

같은 메시지가 중복 전송·저장되는 것을 막는 장치도 아직 없습니다. 또한 현재 서버는 테스트 API 수신까지만 확인한 상태로, 실제 매매일지 DB 저장 기능과는 구분됩니다.

08 · 향후 개발

남은 과제

자동 트리거 검증이 먼저, 그다음이 서버 쪽 분석과 DB 연결입니다.
